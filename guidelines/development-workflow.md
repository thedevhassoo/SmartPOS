# Development and release workflow
Product quality and development process are both important. Build exactly 20 meaningful end-to-end slices, five per engineer; never build all UI then all backend. Validate context before coding. For each slice: select and load only relevant context; refine criteria and checks; select HITL or bounded AFK; implement; run functional, negative and applicable EP/BVA tests; human review Accept/Revise/Reject; integrate accepted candidate; update plan and context. Gates G1 readiness, G2 functional, G3 architecture, G4 regression/integration, G5 final end-to-end/NFR. Supporting design generated as needed; human approval needed for consequential decisions, not every detailed artefact. Keep original AI conversations and Git history as evidence; logs reference actual session, owner, mode/reason, criteria, iterations, test commands/outcomes, human decisions, issues, plan version, integration commit. Never fabricate evidence. Preserve each meaningful plan version or retrievable Git history; use both numbered snapshots and commits here. Final product must run on LAN; document real commands, access, limitations and actual verification. Final report includes implemented scope, architecture, challenges, limitations, contributions and CCP analysis: problem, complexity drivers, trade-off, two alternatives, integration, evaluation metric, scalability/feasibility, ethical/societal impact. Every engineer understands whole product. Do not commit secrets or real customer data. These guidelines summarize workflow requirements; retain original instructions separately for assessment and verify all mandatory conditions against them.
