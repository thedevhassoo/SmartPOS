# SmartPOS — barcode scanner integration brief (proposed for approval)
Baseline FR-02 supports actual scanning, manual barcode entry and product-name lookup; FR-03 governs Draft Bills. Proposed hardware: USB HID keyboard-wedge scanner connected to each cashier workstation, configured to send barcode characters plus Enter. No driver/backend scanner service, no camera, no WebUSB/WebSerial commitment; a compatible scanner appears as a keyboard. Confirm physical device availability and suffix configuration. Barcode is an opaque string, preserve leading zeros, no numeric coercion, trim only agreed framing/suffix, unique database constraint. Do not impose arbitrary EAN/UPC checksum or length unless requirements approve it.
S03: shared accessible barcode input, scan/manual exact lookup, name fallback, unknown code message, no automatic product creation, authorized registration and duplicate rejection. Enter must submit once, clear/refocus only on appropriate completion; no document-global keystroke hijack.
S09: use the same lookup path to add known product to Draft Bill; proposed repeated scans increment quantity by one, serialized/queued lookup or otherwise lossless processing of rapid intentional repeated scans; do not debounce distinct intended scans away. Prevent duplicate submission for a single terminator. Keep edits and focus safe in dialogs/forms; clear failure feedback and preserve draft. No stock deduction/reservation before Push. S12 recomputes approved offers for scanned items; S13 validates stock and commits completed sale exactly once, retains Draft Bill on failure; no payment processing. S07/S08/S14 retain string barcodes and duplicate rules through CSV. S05/S06 show current location in lookup if authorized. S04/S10 may reuse scan lookup for authorized inventory selection only; not extra functionality.
Tests: valid scan, manual same code, name fallback, unknown code, leading-zero string, duplicate registration, rapid repeated scans, single Enter event, modal/quantity focus, scanner unplugged/manual fallback, stock unchanged in draft, insufficient/concurrent last-item sale, rollback and retry. Automated keyboard event simulation is not physical hardware validation. Test actual scanner in text editor first, then browser against seeded known and unknown codes and rapid scans. Record scanner model, suffix, observed results, date, actual chat and Git reference; if unavailable mark hardware validation pending, not passed. No secrets or identifying customer data in evidence.
